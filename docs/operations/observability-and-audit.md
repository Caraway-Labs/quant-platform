# Observability, audit and runbook standard

All repositories emit structured events with UTC `timestamp`, `level`, `service`/repository, `environment`, `event_type`, `run_id`, `correlation_id`, concise `message`, and where relevant `strategy_id`, `model_version_id`, `error_type`, `retryable`, and bounded non-secret `metadata`. Use stable uppercase snake-case event names. `run_id` identifies one job attempt; `correlation_id` follows a decision from data manifest through prediction, execution and broker reconciliation. Persist `data_version`/dataset manifest reference, `order_intent_id`, broker client order id and `broker_order_id` where applicable. Retries receive new attempt ids but retain correlation and stable intent/client ids.

| Repository | Required event families | Operational signals |
| --- | --- | --- |
| `quant-data` | DATA_INGEST_STARTED/COMPLETED, DATA_QUALITY_FAILED, DATA_PUBLISHED | Freshness, source lag, row counts, failed loads, quality failures and revision volume. |
| `quant-research` | TRAINING_STARTED/COMPLETED, BACKTEST_COMPLETED, MODEL_APPROVED, PREDICTION_PUBLISHED/REJECTED | Failed experiments, pinned model/data traceability, approval state changes and stale prediction count. |
| `quant-execution` | EXECUTION_RUN_STARTED/COMPLETED, SIGNAL_REJECTED, RISK_REJECTED, ORDER_INTENT_CREATED, ORDER_SUBMITTED, ORDER_PARTIALLY_FILLED, ORDER_FILLED, ORDER_CANCELLED, BROKER_ERROR, RECONCILIATION_MISMATCH, EXECUTION_HALTED | Scheduled run success, rejected signals/risk, order failures, broker connectivity, stale signals, reconciliation mismatches and halt state. |

`INFO` records expected progress and successful audit events. `WARNING` records recoverable degradation requiring routine review. `ERROR` records failed runs or controls requiring owner response. `CRITICAL` records potential unauthorized/duplicate orders, uncertain submission, live credential exposure, unreconciled position/account divergence or failed kill switch; halt affected execution and alert the on-call operator immediately. Stale/unapproved predictions and risk vetoes are expected per-item events; escalate repeated/systemic patterns or any live exposure. Failed critical data freshness, Snowflake outage during execution and broker outage affecting order certainty alert immediately. Exact numeric alert thresholds belong in reviewed operational configuration, not implicit code defaults.

## Reconstructable audit

Before broker submission, persist order intent with stable client id, approved strategy/model version, prediction and data manifest, target, mode/account and correlation id; persist deterministic risk-policy version, inputs, decision and reason. Record submission attempts, broker acknowledgements or uncertainty, status transitions, fills, positions/account snapshots, reconciliations and operator interventions as linked immutable events. Human approval/promotion/demotion records include actor, evidence, effective time and configuration change reference. Never silently overwrite a decision; append a correction with predecessor link. Retain data/model/config versions and events for the applicable legal/operational period, with an explicit policy in each owning repository; no purge may break reconstruction of a retained execution. Restrict audit access and redact credentials and sensitive account details in logs.

## Incident and runbook interface

Every runbook identifies detection, owner, immediate safety action, evidence to preserve, broker/Snowflake verification, escalation, recovery gate and post-incident record. Required child-owned runbooks are indexed in [operations](README.md). A halted flow resumes only after cause and current broker/account state are known, reconciliation is clean, required credentials/configuration are valid and an authorized operator records the decision. Never retry an uncertain order submission using a new client id before broker lookup and reconciliation. Snowflake outage, stale data or invalid approval halts dependent new submissions; preserve evidence and reconcile after recovery. `quant-data` owns source-quality incidents; `quant-research` owns model/approval defects; `quant-execution` owns broker, risk, order and account incidents. Cross-boundary incidents coordinate all affected owners.
